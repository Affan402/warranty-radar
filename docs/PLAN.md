Gates arrive in stages. Phase 0 enforces ruff (format and lint), mypy and pytest. Phase 1 adds coverage, pip-audit and bandit, plus Testcontainers integration tests. Phase 2 adds the web gates (eslint, prettier, tsc, vitest, Playwright). Phase 3 adds buf lint and breaking checks. The eval gate arrives in Phase 7.
Definition of done for every PR
[ ] Small, single-purpose branch with a conventional commit title (feat:, fix:, refactor:)
[ ] Tests cover the happy path and at least one failure path
[ ] Errors handled and re-raised with context (raise ... from err); no swallowed errors
[ ] Every query is scoped to the authenticated user (no cross-user access)
[ ] Inputs validated at the edge; no secrets in code or logs
[ ] Structured logs with request ID; timeouts on every outbound call
[ ] Migration added if the schema changed; docs/ADR updated if a decision changed
[ ] AI review done and findings resolved; you can explain every line
Non-functional requirements to keep in mind: reliability, security, scalability, maintainability, observability, testability. Each phase below adds at least one of them deliberately.

Phase 0: Foundations refresher
Learn: TypeScript for JavaScript developers (types, generics, narrowing, zod), SQL beyond the basics (joins, indexes, EXPLAIN, transactions, Postgres vs MySQL), modern Python (type hints, Pydantic v2, asyncio, context managers, pytest, uv). Resources: TypeScript Handbook, PostgreSQL Tutorial, FastAPI docs tutorial, Real Python asyncio guides.
Build:
[ ] A small FastAPI app with two async endpoints, Pydantic validation and pytest tests
[ ] A Postgres schema for Paperless with three queries you can explain using EXPLAIN
[ ] Monorepo skeleton (see "Repo layout" under Engineering standards), Makefile, CLAUDE.md, docs/PLAN.md
[ ] GitHub Actions running ruff (format and lint), mypy and pytest on playground/fastapi-app now and on apps/ later (web job ready for Phase 2)
[ ] ADR-001: why one API service plus one ML service
AI role: Tutor only. Autocomplete off. Ask for explanations and exercises; write every line yourself.
Done when: you can explain sync vs async endpoints in FastAPI, and write an endpoint with Pydantic validation and a pytest test without help.
Phase 1: Core API (FastAPI + Postgres + auth)
Learn: project structure (router → service → repository), dependency injection with Depends, Pydantic v2 schemas, SQLAlchemy 2.0 async + Alembic migrations, JWT access + refresh tokens with rotation, password hashing (argon2id), cursor pagination, OpenAPI (generated by FastAPI).
Build:
[ ] Postgres + Redis via docker-compose; Alembic migrations for users, receipts, receipt_items, warranties
[ ] Endpoints: sign up, log in, refresh, log out; receipts CRUD with manual entry; list with cursor pagination and filters
[ ] Auth dependency; every query scoped by user_id
[ ] Consistent JSON error format via exception handlers
[ ] Integration tests against real Postgres with Testcontainers and pytest-asyncio; CI adds coverage, pip-audit and bandit
[ ] Rate limiting on auth endpoints (Redis)
AI role: Tutor for the first router, service and repository. Pair for the rest. Delegate only for repetitive CRUD after you have written one by hand.
Done when: a test proves user A cannot read, update or delete user B's receipt; CI is green.
Phase 2: Web app + first deploy
Learn: Next.js App Router, server vs client components, route handlers, auth with httpOnly cookies, TanStack Query, forms with react-hook-form + zod. You know React and Express, so focus on what is different: server components and where auth state lives.
Build:
[ ] Auth pages, receipts list, receipt detail, manual entry form
[ ] Typed API client generated from the OpenAPI spec
[ ] Playwright end-to-end test: sign up → add receipt → see it in the list
[ ] Deploy API + DB + web to a staging environment; secrets in the platform's secret store
AI role: Pair, moving to Delegate for UI components (you know React). Review accessibility and loading/error states.
Done when: a friend can sign up on the live URL and add a receipt.
Phase 3: ML service + gRPC
Learn: why a separate service (heavy dependencies, independent scaling and releases), Protobuf design, buf, gRPC in Python (grpcio, async), deadlines, retries with backoff, status codes; OCR; LLM structured output validated with Pydantic; presigned URLs for S3/MinIO.
Build:
[ ] proto/ml/v1/extractor.proto: ExtractReceipt(image_ref) → merchant, date, currency, items, total, warranty_hints, confidence
[ ] Upload flow: web gets a presigned URL from the API, uploads the image to MinIO, the API records it
[ ] ML service gRPC server: OCR → LLM → Pydantic validation; FastAPI exposes /healthz and /metrics
[ ] The API calls the ML service with a 30 s deadline and 2 retries; on failure the receipt stays editable manually
[ ] Upload validation: file type by magic bytes, size limit, image re-encoding
[ ] A test set of 20 of your own receipts with expected values in docs/evals
[ ] ADR-002: why gRPC and a separate service
AI role: Tutor for Protobuf and the first gRPC round trip. Pair for OCR/LLM code.
Done when: a photo becomes a filled-in receipt in the UI, and stopping the ML service degrades gracefully instead of crashing.
Phase 4: Async jobs, events, reminders
Learn: event-driven design and task queues (Celery + Redis broker), at-least-once delivery, idempotency, the outbox pattern, scheduled jobs (Celery beat), retries with backoff, graceful shutdown.
Build:
[ ] Upload creates a job; extraction runs asynchronously on a Celery worker; the UI shows status (processing / done / needs review)
[ ] Outbox table so jobs are never lost when the DB write succeeds
[ ] Idempotent tasks (processing the same job twice changes nothing)
[ ] Reminders 7 days and 1 day before deadlines via Celery beat, sent by email (Resend or SMTP)
[ ] Failed-job handling: retry policy plus a dead-letter queue or table
[ ] ADR-003: why Celery + Redis, and what would change it (RabbitMQ, Kafka)
AI role: Pair. Ask AI to list failure scenarios before you write code, then test each one.
Done when: killing the worker mid-job and restarting it produces no lost and no duplicate reminders.
Phase 5: GraphQL dashboard
Learn: schema design, Strawberry resolvers, the N+1 problem and dataloaders, query depth and complexity limits, codegen on the client.
Build:
[ ] /graphql endpoint in the FastAPI service, sharing the same service layer as REST
[ ] Queries: spending by category/month, receipts with items and warranties, upcoming deadlines
[ ] Dataloaders; depth and complexity limits; auth enforced in resolvers
[ ] Dashboard page with charts in Next.js
[ ] ADR-004: why both REST and GraphQL
AI role: Tutor for the first schema and resolver, then Pair.
Done when: the dashboard loads in a single request with no N+1 queries (verified in logs).
Phase 6: AI layer
Learn: raw LLM APIs first (tool calling, structured output), then LangGraph (state, nodes, conditional edges, checkpoints, human-in-the-loop), embeddings and pgvector, evals, Langfuse tracing.
Build:
[ ] Rebuild extraction as a LangGraph graph: OCR → extract → validate (items sum to total, valid date) → retry with feedback (max 2) → else flag for human review
[ ] "Needs review" screen where the user confirms or corrects fields; corrections are saved for evals
[ ] Embeddings in pgvector; semantic search ("that charger from the mall")
[ ] "Ask your receipts" assistant with tools that call your API, always scoped to the current user; no raw SQL from the LLM
[ ] Eval script over your test set reporting accuracy per field, cost and latency
[ ] Langfuse traces for every LLM call
AI role: Tutor for LangGraph concepts, Pair for implementation. Write the eval set yourself.
Done when: you can show a before/after accuracy number for a prompt or model change.
Phase 7: MLOps
Learn: experiment tracking (MLflow), versioning prompts and models with a registry and rollback, containerized model serving, CI/CD with quality gates, Kubernetes basics on k3s (Deployments, Services, ConfigMaps and Secrets, probes, autoscaling), Prometheus and Grafana, drift and quality monitoring, cost tracking.
Build:
[ ] MLflow server in docker-compose; the eval script logs every run (model, prompt version, per-field accuracy, cost, latency)
[ ] Versioned prompts and model settings; promote one version to "production" through config, with a tested rollback
[ ] Eval gate in CI: block the merge when accuracy drops below the baseline
[ ] ML service image with pinned dependencies, plus health and readiness probes
[ ] Deploy API, worker and ML service to k3s with manifests (or Helm)
[ ] Prometheus + Grafana: latency, extraction success rate, confidence distribution, cost per receipt
[ ] A quality alert: fire when the human-correction rate rises (a practical drift signal)
[ ] ADR-005: self-managed k3s vs a managed platform
AI role: Tutor for MLflow and Kubernetes concepts, then Pair. Write the alert thresholds yourself.
Done when: you can change a prompt, see the accuracy change in MLflow, watch CI block a regression, roll back a bad version, and see the effect on a Grafana dashboard.
Phase 8: Production readiness + launch
Learn: OpenTelemetry tracing and metrics, dashboards and alerts, OWASP Top 10, backups, load testing.
Build:
[ ] OpenTelemetry traces across Next → API → Celery worker → ML service; Grafana dashboards for latency, error rate and queue depth
[ ] Security pass: OWASP Top 10 checklist, security headers, CORS, dependency scanning, secret rotation
[ ] Load test with k6; fix the top bottleneck
[ ] Automated Postgres backups and a tested restore
[ ] Production deploy with a custom domain; demo account with sample data
[ ] README with architecture diagram, ADR links, screenshots, and a 2-minute demo video
